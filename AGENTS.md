# AGENTS.md

Instructions for coding agents (Claude Code, Codex, Cursor, etc.) working in this
repository. Read thoroughly before proposing or making any changes.

## What is this project

Open-source grounded search and factual synthesis engine (LLM) whose primary goal is rigorously substantiated knowledge: virtually every factual claim in a response is accompanied by a verifiable primary or secondary source cited inline in markdown format `[Source Title](URL)`.
See `README.md` and [`decisions/0001-goal-and-scope.md`](decisions/0001-goal-and-scope.md).

## Language

Documentation, Architecture Decision Records (`decisions/`), READMEs, code, docstrings, comments, and identifiers are strictly in English.

## How decisions are recorded

`decisions/` is the single source of truth for all project goals, architecture, and design, structured as ADRs (Architecture Decision Records) — start with [`decisions/README.md`](decisions/README.md).

- One markdown file per decision, sequentially numbered (`NNNN-title.md`); never reorder or reuse numbers. Use `decisions/template.md` as the baseline.
- Standard sections: **Status** (Proposed | Accepted | Superseded), **Date**, **Context**, **Decision**, **Consequences**.
- **Refinement of an existing decision** (category change, scope expansion, detail correction): append a section `## Revision (YYYY-MM-DD): <what changed>` at the end of the existing ADR — do not create a new ADR, do not rewrite historical text as if previous versions never existed.
- **Reversal of an accepted decision**: create a new ADR that references and supersedes the old one.
- After creating or revising an ADR, **update the index table in `decisions/README.md`** (number/title/status).
- Before proposing a new decision, verify whether it is already covered in another ADR to avoid duplicate context — reference existing ADRs instead of repeating their content.

## Implementation workflow: mandatory prior approval

No implementation, script, configuration, or code change may be executed autonomously without explicit user approval. The workflow strictly follows this pipeline:

1. **"I plan to do it this way"**: the agent details the proposed action plan (what to do, how, which files/configs will be altered, commands to run, and the rationale).
2. **Iterative loop with the user**: discuss, align options, and decide on the best approach.
3. **Implementation**: only after explicit user approval are changes executed.

## Before stating technical facts (licenses, pricing, library capabilities, API state)

Perform a search before asserting technical facts in an ADR or response, citing the source as an inline markdown link. The project demands verified sources for all claims generated by the product ([0001](decisions/0001-goal-and-scope.md), [0005](decisions/0005-source-verification-and-citation.md)) — the same standard applies to those building it. Do not assume third-party licenses or pricing tiers remain unchanged without checking.

## Before adding a dependency, model, or external service, check in this order

1. **Permissive license compatible with general open research**:
   Open-weight models such as Llama (3.1/3.2/3.3), Qwen (2.5), Mistral, and DeepSeek are supported ([0003](decisions/0003-llm-model-architecture.md)). Python libraries should favor Apache 2.0, MIT, or BSD licenses.
2. **Privacy and local sovereignty**:
   The engine is *local-first*: favor integration with self-hosted search (SearXNG) and local inference or standard OpenAI-compatible endpoints without proprietary lock-in.
3. **Commercial or cloud services**:
   When configured (e.g., validation with `gemini-2.5-flash` per [0011](decisions/0011-pipeline-validation-with-commercial-model.md)), they must operate via decoupled universal protocols (OpenAI Chat Completions over `httpx`), allowing users to switch between cloud and local providers simply by adjusting `.env` variables.

## Philosophy: measure before optimizing/building

Do not build the most complex or generic solution upfront. Prototype the simplest version that solves the common case, measure its performance in practice, and add complexity only when demonstrably necessary. See [0007](decisions/0007-response-pipeline-orchestration.md), [0009](decisions/0009-source-content-extraction.md), and [0010](decisions/0010-citation-verification-ragas-nli.md) as examples.

## Git

- **Never run `git commit` or `git push`.** The user manages version control personally. Prepare changes, run tests, and conclude by providing a suggested commit message — the commit itself is always made by the user.
- When removing dead or obsolete code, delete it completely instead of commenting it out — git history preserves past code.

## Terminology matters

Directory, file, and field names must accurately reflect their contents. If a name no longer matches reality, flag it and propose a coherent rename across the entire repository.

## Test prompts (`prompts/`)

`prompts/prompts_vN.yaml` is the versioned evaluation suite for the search and synthesis engine, structured into categories documented in [`prompts/README.md`](prompts/README.md):
- `trivial`: universal factual sanity check.
- `open-research`: multidisciplinary synthesis across science, health, history, technology, and public policy.
- `long-tail`: retrieval on regional statistical data and niche scientific/ecological queries.

## Testing

When modifying Python code (`search-proxy/`), run the real test suite (`.venv/bin/python -m pytest -q`) before reporting completion — never assume tests pass.

## Repository structure

- `decisions/` — ADRs, single source of truth for objectives, architecture, and product decisions
- `prompts/` — versioned benchmark prompt suites (`prompts_vN.yaml`)
- `search-proxy/` — Python package: canonical search (SearXNG) + ethical extractor (HTML/PDF) + grounded synthesis (OpenAI-compatible)
- `results/` — raw output from evaluation runs, stored as immutable subdirectories per run
